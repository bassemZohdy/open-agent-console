# API guide

The API is intended for the control panel and local automation. The authoritative machine-readable contract is docs/api-reference.json; this guide explains the behavior and common request flows.

## General behavior

- Base path: /api.
- Request and response bodies use JSON unless an endpoint returns SSE.
- All request payloads are validated with Zod.
- Every request has an x-correlation-id. If the caller does not send one, the server creates it.
- Error responses include an error message, a code, and a correlationId when the response is generated by the application.
- The application is unauthenticated. Do not expose the API directly to an untrusted network.

## Health and settings

    curl http://127.0.0.1:3000/api/health
    curl http://127.0.0.1:3000/api/ready
    curl http://127.0.0.1:3000/api/settings

Health confirms that the process is responding. Readiness executes a SQLite query and returns HTTP 503 when the database is unavailable. Settings reports the application version, persistence mode, database path, and transfer behavior without exposing credentials.

## Registry endpoints

The registry resources support validated list/create/update/delete operations where applicable:

| Resource | Collection | Item operations |
| --- | --- | --- |
| Models | GET/POST /api/models | PUT/DELETE /api/models/:id, POST /api/models/:id/test |
| Skills | GET/POST /api/skills | PUT/DELETE /api/skills/:id |
| Tools | GET/POST /api/tools | PUT/DELETE /api/tools/:id, POST /api/tools/validate |
| MCP servers | GET/POST /api/mcp-servers | PUT/DELETE /api/mcp-servers/:id, POST /api/mcp-servers/:id/discover |
| Memory connectors | GET/POST /api/memory-connectors | PUT/DELETE /api/memory-connectors/:id |
| Agents | GET/POST /api/agents | PUT/DELETE /api/agents/:id, PATCH /api/agents/:id/enabled, POST /api/agents/:id/duplicate |

Use the schemas in docs/api-reference.json for exact field constraints. IDs are UUIDs returned by the create response.

## Agent composition

Agent skill and tool mappings are replaced as ordered arrays:

    PUT /api/agents/:id/skills
    { "skillIds": ["skill-id-1", "skill-id-2"] }

    PUT /api/agents/:id/tools
    { "toolIds": ["tool-id-1"] }

Inspect the composed prompt without starting a run:

    GET /api/agents/:id/effective-prompt

The prompt contains agent instructions, enabled skills in mapping order, and bounded long-term memory. Disabled skills/tools remain in the registry but are ignored by runtime resolution.

## Memory

List and manage long-term memory for an agent:

    GET /api/agents/:id/memories
    POST /api/agents/:id/memories
    PUT /api/agents/:agentId/memories/:memoryId
    DELETE /api/agents/:agentId/memories/:memoryId

Memory is separate from session history. A memory row has optional key text, required content, and JSON metadata. The none connector always returns an empty memory set.

## Registry transfer

Export configuration:

    curl -o registry.json http://127.0.0.1:3000/api/registry/export

Import the file:

    curl --fail -X POST \
      -H 'content-type: application/json' \
      --data-binary @registry.json \
      http://127.0.0.1:3000/api/registry/import

Transfer format version 1 contains models, agents, skills, tools, MCP servers, memory connectors, and mappings. It excludes credentials, secret-like header values, long-term memories, sessions, messages, runs, and tool calls. Imports are deterministic and report created/updated counts.

## Sessions and runs

List sessions with optional agent and pagination filters:

    GET /api/sessions?agentId=<uuid>&offset=0&limit=25

Rename or delete a session:

    PATCH /api/sessions/:id
    DELETE /api/sessions/:id

Read its messages:

    GET /api/sessions/:id/messages

List runs with optional agent/status filters and pagination:

    GET /api/runs?agentId=<uuid>&status=completed&offset=0&limit=25

Inspect one run, including persisted tool calls:

    GET /api/runs/:id

Run statuses are running, completed, failed, and cancelled. A completed run can still have contextTruncated set when history or prompt bounds were applied.

## Chat SSE

Start a new session:

    curl --no-buffer --fail -X POST \
      -H 'content-type: application/json' \
      -H 'accept: text/event-stream' \
      -d '{"message":"hello"}' \
      http://127.0.0.1:3000/api/agents/<agent-id>/chat

Continue a session by including sessionId:

    { "message": "continue", "sessionId": "<session-id>" }

The stream uses media type text/event-stream. Each event has a JSON data payload and version 1. Events are:

| Type | Fields | Meaning |
| --- | --- | --- |
| session | sessionId, runId, correlationId | IDs available before model execution |
| token | text | Incremental assistant output |
| usage | inputTokens, outputTokens, totalTokens | Provider usage when available |
| done | sessionId, runId | Successful completion |
| cancelled | sessionId, runId | Abort signal was observed |
| error | message, code, correlationId | Failed execution |

The client should preserve partial frames across network chunks, append token text in order, and use the final event to refresh session/run state.

## Error handling

Typical status classes are:

- 400 for invalid request data;
- 404 for an unknown resource;
- 409 for protected references or conflicting state;
- 413 for oversized request bodies; and
- 500/503 for runtime or readiness failures.

Use the response code and correlationId when searching server logs. Do not display raw provider credentials or internal stack traces to end users.

## Contract maintenance

When a route or request schema changes:

1. update the route and its tests;
2. run npm run api:generate;
3. review docs/api-reference.json;
4. run npm run api:check; and
5. update this guide and README.md when behavior is user-visible.
