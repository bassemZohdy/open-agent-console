# API guide

The API is intended for the control panel and local automation. The authoritative machine-readable contract is docs/api-reference.json; this guide explains the behavior and common request flows.

## General behavior

- Base path: /api.
- Request and response bodies use JSON unless an endpoint returns SSE.
- All request payloads are validated with Zod.
- Every request has an x-correlation-id. If the caller does not send one, the server creates it.
- Error responses include an error message, a code, and a correlationId when the response is generated by the application.
- When credential accounts are configured, all non-public API routes require the HttpOnly session cookie issued by `/api/auth/login`. Do not expose the API directly to an untrusted network.

## Authentication

    curl -i -c cookies.txt -H "Content-Type: application/json" \
      -d '{"username":"admin","password":"admin"}' \
      http://127.0.0.1:3000/api/auth/login
    curl -b cookies.txt http://127.0.0.1:3000/api/auth/me
    curl -X POST -b cookies.txt http://127.0.0.1:3000/api/auth/logout

The demo credentials are read from environment variables. Invalid credentials return a generic `401` response. Health, readiness, login, logout, and the current-session endpoint remain public so the UI can establish access state.

## Health and settings

    curl http://127.0.0.1:3000/api/health
    curl http://127.0.0.1:3000/api/ready
    curl http://127.0.0.1:3000/api/settings

Health confirms that the process is responding. Readiness executes a SQLite query and returns HTTP 503 when the database is unavailable. Settings reports the application version, persistence mode, database path, and transfer behavior without exposing credentials.

### A2A exposure management

The A2A management endpoints are admin-only:

    GET /api/a2a/exposures
    POST /api/a2a/exposures
    PUT /api/a2a/exposures/:id
    DELETE /api/a2a/exposures/:id

An exposure belongs to one agent and has a unique lowercase kebab-case slug. New records are private, unpublished, and disabled. Publication and enablement are independent switches, so an administrator can pause a published interface without deleting its policy or task history. `authEnv` is only the name of an environment variable containing the bearer credential; raw tokens are never accepted or returned.

The exposure payload includes a safe agent summary and never includes the agent's instructions, memory configuration, or internal tool mappings.

### A2A HTTP+JSON transport

Published and enabled exposures are available under `/a2a/:slug`. The transport is independent of the console session cookie and UI roles. For bearer exposures, callers send `Authorization: Bearer <credential>`; for public exposures configured with `authMode: none`, no credential is required. Private/internal Agent Cards require the same bearer credential; a public card contains no secrets or internal instructions.

All operations except Agent Card discovery require `A2A-Version: 1.0` and use `application/a2a+json`. Unsupported versions return `VersionNotSupportedError`. The current slice supports text parts only, declares `pushNotifications: false` and `extendedAgentCard: false`, and uses `text/plain` as its default input/output mode.

    GET  /a2a/:slug/.well-known/agent-card.json
    POST /a2a/:slug/message:send
    POST /a2a/:slug/message:stream
    GET  /a2a/:slug/tasks
    GET  /a2a/:slug/tasks/:taskId
    POST /a2a/:slug/tasks/:taskId:cancel
    POST /a2a/:slug/tasks/:taskId:subscribe

Submit a message with an idempotent client message ID:

    curl --fail -X POST \
      -H 'content-type: application/a2a+json' \
      -H 'a2a-version: 1.0' \
      -H 'authorization: Bearer <credential>' \
      -d '{"message":{"messageId":"client-001","role":"ROLE_USER","parts":[{"text":"Summarize the release notes"}]}}' \
      http://127.0.0.1:3000/a2a/<slug>/message:send

The task returns a stable `id` and `contextId`. Poll the task until the status state is `TASK_STATE_COMPLETED`, `TASK_STATE_FAILED`, or `TASK_STATE_CANCELED`, or use the SSE stream/subscription. The task manager maps the A2A context to an application session and maps runtime execution to a run with the request correlation ID. Retrying the same `messageId` for the same exposure and caller returns the original task.

The server enforces the configured request-per-minute, concurrent-task, max-task-seconds, and global request body limits. Audit records contain lifecycle action, exposure/task references, caller fingerprint, and timestamps; they do not store bearer credentials or message content by default.

Use the schemas in docs/api-reference.json for exact field constraints. IDs are UUIDs returned by the create response.

## Agent composition

Agent skill and tool mappings are replaced as ordered arrays:

    PUT /api/agents/:id/skills
    { "skillIds": ["skill-id-1", "skill-id-2"] }

    PUT /api/agents/:id/tools
    { "toolIds": ["tool-id-1"] }

Inspect the composed prompt without starting a run:

    GET /api/agents/:id/effective-prompt

The prompt contains agent instructions, enabled skills in mapping order, and bounded long-term memory. Disabled skills/tools remain in the registry but are ignored by runtime resolution.

## Memory

List and manage long-term memory for an agent:

    GET /api/agents/:id/memories
    POST /api/agents/:id/memories
    PUT /api/agents/:agentId/memories/:memoryId
    DELETE /api/agents/:agentId/memories/:memoryId

Memory is separate from session history. A memory row has optional key text, required content, and JSON metadata. The none connector always returns an empty memory set.

## Registry transfer

Export configuration:

    curl -o registry.json http://127.0.0.1:3000/api/registry/export

Import the file:

    curl --fail -X POST \
      -H 'content-type: application/json' \
      --data-binary @registry.json \
      http://127.0.0.1:3000/api/registry/import

Transfer format version 1 contains models, agents, skills, tools, MCP servers, memory connectors, and mappings. It excludes credentials, secret-like header values, A2A exposure policy, long-term memories, sessions, messages, runs, and tool calls. Imports are deterministic and report created/updated counts.

## Sessions and runs

List sessions with optional agent and pagination filters:

    GET /api/sessions?agentId=<uuid>&offset=0&limit=25

Rename or delete a session:

    PATCH /api/sessions/:id
    DELETE /api/sessions/:id

Read its messages:

    GET /api/sessions/:id/messages

Each message includes an `attachments` array containing the safe display
metadata (`name`, `mimeType`, and `size`) for files attached to that message.
The database also retains the bounded extracted text used for model context, so
reopened sessions and later turns continue to reference the attachment. The
original binary file is not uploaded or recoverable from the application.

List runs with optional session/agent/status filters and pagination:

    GET /api/runs?sessionId=<uuid>&agentId=<uuid>&status=completed&offset=0&limit=25

Inspect one run, including persisted tool calls:

    GET /api/runs/:id

Run statuses are running, completed, failed, and cancelled. A completed run can still have contextTruncated set when history or prompt bounds were applied.

## Chat SSE

Start a new session:

    curl --no-buffer --fail -X POST \
      -H 'content-type: application/json' \
      -H 'accept: text/event-stream' \
      -d '{"message":"hello"}' \
      http://127.0.0.1:3000/api/agents/<agent-id>/chat

Continue a session by including sessionId:

    { "message": "continue", "sessionId": "<session-id>" }

The optional `attachments` array accepts up to five bounded files. Each item has
`name`, `mimeType`, `size` (maximum 8 MiB), and optional extracted `text`
(maximum 60,000 characters). Text is used as additional context for the current
model turn and is stored with the user message for future turns; attachments are
not persisted as binary files.

    {
      "message": "Summarize these notes",
      "attachments": [{
        "name": "notes.txt",
        "mimeType": "text/plain",
        "size": 42,
        "text": "...bounded extracted text..."
      }]
    }

The stream uses media type text/event-stream. Each event has a JSON data payload and version 1. Events are:

| Type | Fields | Meaning |
| --- | --- | --- |
| session | sessionId, runId, correlationId | IDs available before model execution |
| token | text | Incremental assistant output |
| usage | inputTokens, outputTokens, totalTokens | Provider usage when available |
| done | sessionId, runId | Successful completion |
| cancelled | sessionId, runId | Abort signal was observed |
| error | message, code, correlationId | Failed execution |

The client should preserve partial frames across network chunks, append token text in order, and use the final event to refresh session/run state.

## Error handling

Typical status classes are:

- 400 for invalid request data;
- 404 for an unknown resource;
- 409 for protected references or conflicting state;
- 413 for oversized request bodies; and
- 500/503 for runtime or readiness failures.

Use the response code and correlationId when searching server logs. Do not display raw provider credentials or internal stack traces to end users.

## Contract maintenance

When a route or request schema changes:

1. update the route and its tests;
2. run npm run api:generate;
3. review docs/api-reference.json;
4. run npm run api:check; and
5. update this guide and README.md when behavior is user-visible.
